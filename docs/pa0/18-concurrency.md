# 18 · 동시성

## 동시성 프로그래밍이란 

사람의 사고는 기본적으로 **순차적**이다. 그래서 "시간 순서대로 이렇게 실행되겠지"라는 직관에 의존하는데, 동시성 환경에서는 그 직관이 거의 항상 틀린다. 스케줄러는 프로그래머의 허락을 구하지 않고 임의의 시점에 스레드를 교체하며, 컴퓨터 시스템에서 **일어날 수 있는 모든 실행 순서**를 사람이 머릿속으로 열거하는 일은 오류가 잦고 종종 불가능하다.

동시성 프로그램의 고전적 문제는 세 부류로 나뉜다.

| 문제 | 정의 | 비유 |
|---|---|---|
| **레이스(Race)** | 결과가 시스템 다른 곳의 임의적인 스케줄링 결정에 의존한다 | 비행기 마지막 좌석을 누가 차지하는가 |
| **데드락(Deadlock)** | 잘못된 자원 할당으로 어떤 스레드도 전진하지 못한다 | 교차로 한복판에서 서로를 막은 교통 정체 |
| **라이브락 / 굶주림(Starvation)** | 시스템 전체는 전진하지만 특정 주체가 무한히 기다린다 | 계속 새치기당해 순서가 오지 않는 줄 |

굶주림은 특히 헷갈리기 쉽다. 노란 차가 초록 차에게 양보해야 하고 초록 차가 끊임없이 흘러오면, **전체 시스템은 정상적으로 진행**하지만 노란 차는 영원히 기다린다. 즉 "시스템이 살아 있다"는 사실이 "모든 참여자가 공평하게 진행한다"를 뜻하지 않는다.

!!! example "데드락의 실제 예: 시그널 핸들러에서 `printf`"
    ```c
    void catch_child(int signo) {
        printf("Child exited!\n");   // printf/puts에 재진입! 데드락 위험
        while (waitpid(-1, NULL, WNOHANG) > 0) continue;
    }
    ```
    `printf`의 내부 구현은 대략 *락 획득 → 작업 → 락 해제*이다. 그런데 락을 잡은 직후 시그널이 도착해 핸들러가 실행되고, 핸들러가 다시 `printf`를 호출하면 **같은 스레드가 이미 자기가 잡고 있는 락을 다시 기다린다.** 아무도 그 락을 놓아줄 수 없으므로 프로그램은 그 자리에서 멈춘다. 핸들러 안에서 비동기 시그널 안전(async-signal-safe)하지 않은 함수를 부르지 말라는 규칙이 여기서 나온다.

그럼에도 동시성은 피할 수 없다. 코어 수가 늘어나는 방향으로 하드웨어가 발전하는 한, 동시성은 **점점 더 필수적인** 기법이다. 어려움을 이해하는 것이 회피하는 것보다 낫다.

## 3.7.2 무엇이 공유되는가

스레드는 코드·데이터·힙·커널 컨텍스트를 공유하고, 각자 스택과 레지스터를 갖는다. 하지만 여기서 흔한 오해가 생긴다.

!!! warning "'전역 변수는 공유, 스택 변수는 사적'은 틀린 요약이다"
    개념적으로는 각 스레드의 스택이 사적(private)이지만, **실제로는 분리가 강제되지 않는다.** 레지스터 값만 진짜로 보호되며, 스택은 모두 같은 가상 주소 공간에 있으므로 **어떤 스레드든 다른 스레드의 스택을 읽고 쓸 수 있다.** 개념 모델과 실제 동작의 이 불일치가 혼란과 버그의 근원이다.

그래서 공유는 선언 위치가 아니라 **참조 관계**로 정의한다.

!!! note "정의: 공유 변수"
    변수 `x`는 **여러 스레드가 `x`의 어떤 인스턴스를 참조할 때, 그리고 그때에만** 공유된다.

이 정의를 적용하려면 세 가지를 알아야 한다: (1) 스레드의 메모리 모델, (2) 변수의 인스턴스가 메모리에 어떻게 매핑되는가, (3) 각 인스턴스를 몇 개의 스레드가 참조하는가.

### 변수 인스턴스의 매핑 규칙

| 종류 | 선언 위치 | 인스턴스 개수 |
|---|---|---|
| 전역 변수 | 함수 밖 | 가상 메모리에 정확히 **1개** |
| 지역 자동 변수 | 함수 안, `static` 없음 | **스레드 스택마다 1개** |
| 지역 정적 변수 | 함수 안, `static` 있음 | 가상 메모리에 정확히 **1개** |
| `errno` | 함수 밖이지만 특별 취급 | **스레드마다 1개** |

지역 정적 변수가 함정이다. 선언은 함수 안에 있어 사적으로 보이지만 인스턴스는 하나뿐이므로, 그 함수를 여러 스레드가 실행하면 **공유된다.**

### 예제 분석

```c
char **ptr;  /* 전역 */

void *thread(void *vargp) {
    long myid = (long)vargp;
    static int cnt = 0;
    printf("[%ld]: %s (cnt=%d)\n", myid, ptr[myid], ++cnt);
    return NULL;
}

int main(int argc, char *argv[]) {
    long i;
    pthread_t tid;
    char *msgs[2] = { "Hello from foo", "Hello from bar" };
    ptr = msgs;
    for (i = 0; i < 2; i++)
        pthread_create(&tid, NULL, thread, (void *)i);
    pthread_exit(NULL);
}
```

인스턴스를 나열하면 이렇다. `i.m`, `msgs.m`은 main 스택의 인스턴스, `myid.p0`/`myid.p1`은 각 피어 스레드 스택의 인스턴스다.

| 인스턴스 | main | peer 0 | peer 1 | 공유? |
|---|---|---|---|---|
| `ptr` | 예 | 예 | 예 | **O** |
| `cnt` | 아니오 | 예 | 예 | **O** |
| `i.m` | 예 | 아니오 | 아니오 | X |
| `msgs.m` | 예 | 예 | 예 | **O** |
| `myid.p0` | 아니오 | 예 | 아니오 | X |
| `myid.p1` | 아니오 | 아니오 | 예 | X |

`msgs`는 main의 **스택**에 있는데도 공유된다. 전역 `ptr`가 그 주소를 가리키고 피어 스레드들이 `ptr`를 통해 접근하기 때문이다. 반대로 `myid`는 지역 자동 변수라서 스레드마다 별도 인스턴스를 가지므로 공유되지 않는다.

### 스레드 인자 전달: 세 가지 방법

공유 판별을 실무에서 가장 자주 틀리는 지점이 인자 전달이다.

=== "① 값을 캐스팅 (OK)"

    ```c
    pthread_create(&tids[i], NULL, thread, (void *)i);   // 생산자
    // ...
    void *thread(void *vargp) {
        hist[(long)vargp] += 1;                          // 소비자
        return NULL;
    }
    ```
    각 스레드가 **값으로** 고유한 인덱스를 받는다. `long` ↔ `void *` 왕복 캐스팅은 안전하다. 숫자 하나처럼 작은 데이터에만 쓴다.

=== "② `malloc`/`free` (OK)"

    ```c
    long *p = malloc(sizeof(long));
    *p = i;
    pthread_create(&tids[i], NULL, thread, p);
    // ...
    void *thread(void *vargp) {
        hist[*(long *)vargp] += 1;
        free(vargp);                    // 소비자가 해제
        return NULL;
    }
    ```
    각 스레드가 **고유한 포인터**를 받는다. 항상 동작하며, 구조체처럼 큰 데이터를 넘길 때는 이 방법이 필수다. 부모가 할당하고 스레드가 해제하는 소유권 규약을 지켜야 한다.

=== "③ 스택 슬롯 주소 (WRONG)"

    ```c
    for (i = 0; i < N; i++)
        pthread_create(&tids[i], NULL, thread, &i);   // 위험!
    ```
    모든 스레드가 main의 `i`를 가리키는 **동일한 포인터**를 받는다. 스레드가 `*(long *)vargp`를 읽는 시점에 main은 이미 `i`를 증가시켰을 수도 있고 아닐 수도 있다. 즉 각 스레드가 고유한 인덱스를 읽을지 **보장이 없다** — 전형적인 데이터 레이스다. (게다가 넘긴 스택 슬롯의 생명주기가 끝났다면 무효한 메모리를 읽게 된다.)

## 3.7.3 데이터 레이스: `cnt++`의 정체

공유 변수는 편리하다. 로깅 정보나 파일 캐시처럼 스레드 간에 자료구조를 쉽게 나눠 쓸 수 있다. 하지만 그 편리함이 곧 위험이다.

```c
static unsigned long cnt = 0;

void *incr_thread(void *arg) {
    unsigned long niters = (unsigned long)arg;
    for (unsigned long i = 0; i < niters; i++)
        cnt++;
    return NULL;
}
```

두 스레드가 각각 `niters`번 증가시키면 `cnt == 2*niters`여야 한다. 실제로 실행하면 종종 그보다 **작은** 값이 나온다.

원인은 `cnt++`가 한 개의 명령어가 아니라는 데 있다. 컴파일된 루프 본문을 보자.

```asm
        movq  (%rdi), %rcx
        testq %rcx, %rcx
        jle   .L2
        movl  $0, %eax
.L3:
        movq  cnt(%rip), %rdx     # L: cnt를 읽는다  (Load)
        addq  $1, %rdx            # U: 레지스터에서 갱신 (Update)
        movq  %rdx, cnt(%rip)     # S: cnt에 되쓴다  (Store)
        addq  $1, %rax
        cmpq  %rcx, %rax
        jne   .L3
.L2:
```

루프 한 번은 진입부 `H`(head), 그리고 **읽기 `L` → 갱신 `U` → 쓰기 `S`**, 마무리 `T`(tail)로 나뉜다. 핵심은 다음 한 문장이다.

!!! danger "핵심 아이디어"
    **명령어의 어떤 인터리빙(interleaving)도 가능하며, 그중 일부는 예상과 다른 결과를 낸다.**

아래 표에서 $I_i$는 스레드 $i$가 명령어 $I$를 실행함을, `%rdx`$_i$는 스레드 $i$의 컨텍스트에 있는 `%rdx` 값을 뜻한다.

=== "정상 인터리빙"

    | 스레드 | 명령어 | `%rdx`₁ | `%rdx`₂ | `cnt` |
    |---|---|---|---|---|
    | 1 | H₁ | – | – | 0 |
    | 1 | L₁ | 0 | – | 0 |
    | 1 | U₁ | 1 | – | 0 |
    | 1 | S₁ | 1 | – | **1** |
    | 2 | H₂ | – | – | 1 |
    | 2 | L₂ | – | 1 | 1 |
    | 2 | U₂ | – | 2 | 1 |
    | 2 | S₂ | – | 2 | **2** |

    스레드 1의 `L·U·S`가 끝난 뒤 스레드 2가 시작했으므로 결과는 2. **OK**

=== "잘못된 인터리빙"

    | 스레드 | 명령어 | `%rdx`₁ | `%rdx`₂ | `cnt` |
    |---|---|---|---|---|
    | 1 | H₁ | – | – | 0 |
    | 1 | L₁ | 0 | – | 0 |
    | 1 | U₁ | 1 | – | 0 |
    | 2 | H₂ | – | – | 0 |
    | 2 | L₂ | – | **0** | 0 |
    | 1 | S₁ | 1 | – | 1 |
    | 2 | U₂ | – | 1 | 1 |
    | 2 | S₂ | – | 1 | **1** |

    스레드 2가 스레드 1의 쓰기 **이전의** 값 0을 읽었다. 두 번 증가시켰지만 결과는 1. 증가 한 번이 **사라졌다**. **Oops!**

!!! warning "테스트로 잡기 어렵다"
    나쁜 인터리빙이 실제로 발생할 확률은 매우 낮다. 하지만 **0은 아니다.** 그래서 데이터 레이스는 개발 중에는 잘 나타나지 않다가 부하가 높은 환경, 다른 코어 수, 다른 컴파일러 최적화에서 재현되며, 재현조차 어렵다. 데이터를 쉽게 공유할 수 있다는 성질은 스레드의 **가장 큰 강점이면서 동시에 가장 큰 약점**이다.

## 3.7.4 진행 그래프: 임계 구역과 위험 영역

인터리빙을 표로 하나씩 나열하는 것은 한계가 있다. **진행 그래프(progress graph)** 는 두 스레드의 실행 상태 공간을 그림으로 본다.

- 각 **축**은 한 스레드 내부 명령어의 순차적 순서를 나타낸다.
- 각 **점**은 가능한 실행 상태 $(\text{Inst}_1, \text{Inst}_2)$이다. 예를 들어 $(L_1, S_2)$는 스레드 1이 $L_1$까지, 스레드 2가 $S_2$까지 완료한 상태다.
- **궤적(trajectory)** 은 합법적인 상태 전이의 나열, 즉 하나의 구체적인 동시 실행이다. 예: $H_1, L_1, U_1, H_2, L_2, S_1, T_1, U_2, S_2, T_2$.
![](./images/tj.png)

여기서 두 개념이 정의된다.

!!! note "임계 구역과 위험 영역"
    ![](./images/critical_unsafe.png)

    - **임계 구역(critical section)**: 공유 변수 `cnt`에 대해 `L`, `U`, `S`가 이루는 명령어 구간. 어떤 공유 변수에 대한 임계 구역의 명령어들은 **서로 인터리빙되어서는 안 된다.**
    - **위험 영역(unsafe region)**: 두 스레드가 동시에 임계 구역 안에 있는 상태들의 집합. 진행 그래프에서 두 임계 구역이 교차하는 직사각형 영역이다.
    - **안전한 궤적**: 어떤 위험 영역에도 들어가지 않는 궤적.
    - **주장**: 궤적이 `cnt`에 대해 **올바른 것은 그것이 안전할 때, 그리고 그때에만**이다.

즉 문제는 "어떻게 위험 영역을 통과하지 않는 궤적만 발생하도록 강제할 것인가"로 환원된다.

## 3.7.5 상호 배제: 뮤텍스

!!! question "질문: 안전한 궤적을 어떻게 보장하는가?"
    **답:** 스레드의 실행을 **동기화(synchronize)** 하여 위험한 궤적이 애초에 생길 수 없게 만든다. 각 임계 구역에 대해 **상호 배타적 접근(mutually exclusive access)** 을 보장해야 한다.

**뮤텍스(mutex, MUTual EXclusion)** 는 잠김(locked) 또는 풀림(unlocked) 두 상태만 갖는 불투명한(opaque) 객체다. 불리언 값이지만 산술 연산을 할 수 없고, 처음에는 풀림 상태이며 연산은 두 가지뿐이다.

- `lock(m)`: 잠겨 있지 않으면 잠그고 반환한다. 잠겨 있으면 풀릴 때까지 기다린 뒤 재시도한다.
- `unlock(m)`: 뮤텍스가 잠긴 상태에서, **그것을 잠근 코드만** 호출할 수 있다. 상태를 풀림으로 바꾼다.

```c
static unsigned long cnt = 0;
static pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void *incr_thread(void *arg) {
    unsigned long niters = (unsigned long)arg;
    for (unsigned long i = 0; i < niters; i++) {
        pthread_mutex_lock(&lock);
        cnt++;                          /* 임계 구역 */
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}
```

**왜 동작하는가?** 뮤텍스의 불변식("동시에 최대 한 스레드만 잠글 수 있다")은 진행 그래프 위에 위험 영역을 **완전히 감싸는 금지 영역(forbidden region)** 을 만든다. 어떤 궤적도 이 영역에 진입할 수 없으므로, 위험 영역에도 도달할 수 없다. 안전성이 **구조적으로** 보장되는 것이다.

!!! tip "잠금 규율"
    - 어떤 공유 변수를 보호하는 뮤텍스는 **모든** 접근 지점에서 일관되게 잡아야 한다. 한 곳만 빠뜨리면 보호는 무의미하다.
    - 임계 구역은 **짧게** 유지한다. 길어질수록 병렬성이 사라진다.
    - 여러 뮤텍스를 잡을 때는 **항상 같은 순서로** 잡는다. 순서가 엇갈리면 3.7.1의 데드락이 된다.

## 3.7.6 원자적 메모리 연산

현대 CPU는 *test-and-set*, *compare-and-swap*, *exchange-and-add* 같은 특수 명령어를 제공한다. 이들은 메모리에 대한 읽기–수정–쓰기(read-modify-write)를 **하드웨어가 데이터 레이스를 막아 주는 방식으로** 수행하며, 뮤텍스나 세마포어 자체도 이 명령어들로 구현된다.

카운터를 증가시키는 것뿐이라면 이 명령어를 직접 쓰는 편이 낫다. C11의 `_Atomic` 한정자가 그 경로를 열어 준다.

```c
static _Atomic unsigned long cnt = 0;

void *incr_thread(void *arg) {
    unsigned long niters = (unsigned long)arg;
    for (unsigned long i = 0; i < niters; i++)
        cnt++;                  /* 소스는 그대로, 생성 코드가 달라진다 */
    return NULL;
}
```

생성되는 어셈블리를 비교하면 차이가 분명하다.

=== "`unsigned long` (레이스 있음)"

    ```asm
    .L3:
            movq  cnt(%rip), %rdx     # L
            addq  $1, %rdx            # U
            movq  %rdx, cnt(%rip)     # S
            addq  $1, %rax
            cmpq  %rcx, %rax
            jne   .L3
    ```
    세 명령어로 쪼개지므로 그 사이에 인터리빙이 끼어들 수 있다.

=== "`_Atomic unsigned long`"

    ```asm
    .L3:
            lock addq $1, cnt(%rip)   # L+U+S가 분할 불가능한 하나의 연산
            addq  $1, %rax
            cmpq  %rcx, %rax
            jne   .L3
    ```
    `lock` 접두사가 붙은 단일 명령어가 읽기·갱신·쓰기를 원자적으로 수행한다. 임계 구역이 명령어 하나로 축소되어 인터리빙될 틈이 없다.

### 정확성의 가격

$10^8$회 증가 실험의 경과 시간이다.

| 방식 | 경과 시간 | 정확성 |
|---|---|---|
| 잠금 없음 (레이스) | **0.48 s** | ❌ 틀린 값 |
| C11 원자적 연산 | **3.41 s** | ✅ |
| 뮤텍스 | **15 s** | ✅ |
| 세마포어 | **27.6 s** | ✅ |

!!! important "읽는 법"
    - 동기화는 **공짜가 아니다.** 가장 빠른 정답(원자적 연산)조차 틀린 코드보다 7배가량 느리고, 뮤텍스는 30배가량 느리다.
    - 그러나 **0.48초에 나오는 틀린 답은 답이 아니다.** 성능 비교의 기준선은 "잠금 없음"이 아니라 "정확한 방식들 사이"여야 한다.
    - 보호할 대상이 **단순한 스칼라 갱신**이라면 원자적 연산이, **여러 변수를 한 번에 일관되게** 바꿔야 한다면 뮤텍스가 맞다. 원자적 연산은 연산 하나만 원자적으로 만들지, 여러 연산에 걸친 불변식은 지켜 주지 않는다.
    - 위 수치는 반복마다 락을 잡는 극단적인 경쟁 상황이다. 임계 구역을 키우거나 스레드별 지역 합계를 두고 마지막에 한 번만 합치면(경쟁 감소) 비용은 크게 달라진다.
