# 03 · 블록 단위로 읽기

!!! abstract "목표"
    테이블 파일이 8 KB 블록의 배열이라는 것, 테이블 전체에 매기는 블록 번호 하나가 어떻게
    (세그먼트, 세그먼트 내부 위치)로 바뀌는지, 그리고 그 위치의 8 KB를 `pread`로 읽는 법을 이해합니다.
    이 장이 끝나면 블록 번호 하나에서 읽을 파일과 위치를 손으로 계산할 수 있어야 합니다.

[지난 장](./02-relation-files.md)에서 테이블이 어느 파일들에 있는지 보았습니다. 이 장에서는 PostgreSQL이 그
파일에서 무엇을 얼마만큼 읽는지를 살펴봅니다. PostgreSQL은 파일을 바이트 단위로 다루지 않습니다. 항상
**블록** 단위입니다. 그 단위가 무엇이고, 블록 하나를 어떻게 읽어 오는지가 이 장의 내용입니다.

---

## 1 · 파일은 8 KB 블록의 배열이다

테이블 파일에는 파일 헤더도, 색인도 없습니다. 처음부터 끝까지 **8192바이트짜리 블록이
빈틈없이 이어져 있을 뿐**입니다. 그래서 파일 크기는 언제나 8192의 배수입니다. 지난 장의 `ls` 결과를
다시 보면 8192, 1,073,741,824(= 131072 × 8192), 185,073,664(= 22592 × 8192)였습니다.

```c title="src/include/pg_config.h:32"
#define BLCKSZ 8192
```

이 상수 하나가 PostgreSQL 저장소의 모든 크기를 정합니다. 페이지 하나가 8 KB이고(04장), 버퍼
풀의 프레임 하나가 8 KB이며, 디스크와 주고받는 I/O의 최소 단위가 8 KB입니다.

블록에는 번호가 있습니다. 파일의 첫 8192바이트가 블록 0, 다음이 블록 1, … 입니다. 세그먼트 파일이
하나뿐이라면 블록 n은 파일의 바이트 `[n × 8192, (n + 1) × 8192)`에 있습니다. 이것이 전부입니다.

```
   segment file 0  (size = nblocks x 8192)

   byte    0        8192      16384     24576     32768
           │         │         │         │         │
           ▼         ▼         ▼         ▼         ▼
           ┌─────────┬─────────┬─────────┬─────────┬─ ─ ─ ─
           │ block 0 │ block 1 │ block 2 │ block 3 │  ...
           └─────────┴─────────┴─────────┴─────────┴─ ─ ─ ─
                     block n = bytes [n*8192, (n+1)*8192)
```

!!! note "Design note"
    왜 바이트가 아니라 블록일까요? 디스크는 원래 섹터 단위로만 읽고 쓰며, 파일 시스템도 페이지
    단위로 캐시합니다. 데이터베이스가 그보다 작은 단위로 I/O를 내면 어차피 밑에서 블록으로
    확대됩니다. 그래서 PostgreSQL은 처음부터 "8 KB 하나를 통째로 읽고, 통째로 쓴다"를 규칙으로
    삼고, 그 8 KB 안을 어떻게 채울지는 다음 장의 페이지 레이아웃에 맡깁니다.

## 2 · 테이블 전체의 블록 번호

세그먼트가 여럿이면 번호 매기기가 한 단계 더 필요합니다. PostgreSQL은 테이블 전체를 **파일이 하나인
것처럼** 번호를 매깁니다. 세그먼트 0의 블록이 0 … 131071, 세그먼트 1의 블록이 131072 … 262143,
이런 식입니다. 이 번호가 `BlockNumber`입니다.

지난 장의 `seg_demo`(153664블록)라면 이렇습니다.

```
   BlockNumber (whole relation)
   0                                131071 131072                   153663
   │                                     │ │                             │
   ▼                                     ▼ ▼                             ▼
   ┌─────────────────────────────────────┐ ┌─────────────────────────────┐
   │  133056       131072 blocks (full)  │ │  133056.1    22592 blocks   │
   └─────────────────────────────────────┘ └─────────────────────────────┘
   0                                131071 0                         22591
   block number inside the segment file
```

전역 번호에서 세그먼트와 세그먼트 내부 블록 번호를 꺼내는 데는 나눗셈 한 번이면 됩니다. PostgreSQL이 블록을
읽을 때 부르는 함수 `mdstartreadv()`의 앞부분이 정확히 그것을 합니다.

```c title="src/backend/storage/smgr/md.c:986"
mdstartreadv(PgAioHandle *ioh,
             SMgrRelation reln, ForkNumber forknum, BlockNumber blocknum,
             void **buffers, BlockNumber nblocks)
{
    …
    v = _mdfd_getseg(reln, forknum, blocknum, false,                      /* ← 몫: 어느 세그먼트 */
                     EXTENSION_FAIL | EXTENSION_CREATE_RECOVERY);

    seekpos = (off_t) BLCKSZ * (blocknum % ((BlockNumber) RELSEG_SIZE));  /* ← 나머지: 세그먼트 내부 위치 */

    Assert(seekpos < (off_t) BLCKSZ * RELSEG_SIZE);
    …
```

`_mdfd_getseg()`에서 몫을 구하는 줄은 이것입니다.

```c title="src/backend/storage/smgr/md.c:1744"
_mdfd_getseg(SMgrRelation reln, ForkNumber forknum, BlockNumber blkno,
             bool skipFsync, int behavior)
{
    …
    targetseg = blkno / ((BlockNumber) RELSEG_SIZE);  /* ← 세그먼트 번호 */

    /* if an existing and opened segment, we're done */
    if (targetseg < reln->md_num_open_segs[forknum])
    {
        v = &reln->md_seg_fds[forknum][targetseg];    /* ← 열어 둔 fd 를 꺼낸다 */
        return v;
    }
    …
```

즉 두 줄입니다.

```
segment number         = blkno / 131072
byte offset in segment = (blkno % 131072) * 8192
```

지난 장의 `seg_demo`에서 블록 140000을 읽는다면 140000 / 131072 = 1, 140000 % 131072 = 8928입니다.
세그먼트 1, 즉 `133056.1` 파일의 바이트 8928 × 8192 = 73,138,176부터 8192바이트가 그 블록입니다.

이 계산이 성립하는 것은 지난 장에서 확인한 규칙, **마지막을 뺀 모든 세그먼트가 정확히
131072블록**이기 때문입니다. 앞쪽 세그먼트 하나라도 짧다면 나눗셈만으로는 위치를 알 수 없습니다.
PostgreSQL이 그 규칙을 지키는 이유가 여기 있습니다.

`_mdfd_getseg()`가 `md_seg_fds[forknum][targetseg]`에서 열어 둔 fd를 꺼내 쓰는 것도 눈여겨봅시다.
세그먼트를 미리 열어 배열에 넣어 두었기 때문에, 블록을 읽을 때마다 파일 이름을 만들고 `open()`을
부를 필요가 없습니다. 지난 장의 `mdnblocks()`가 세그먼트를 차례로 열며 채운 것이 이 배열입니다.

## 3 · 그 자리의 8 KB를 읽는다: `pread`

위치를 알았으니 읽을 차례입니다. PostgreSQL은 결국 이 위치를 `pread(2)`에 넘겨 8 KB를 읽습니다. 모양은
이렇습니다.

```c
ssize_t pread(int fd, void *buf, size_t count, off_t offset);
```

`read(2)`와의 차이는 인자 하나, `offset`입니다. `read`는 파일마다 커널이 기억하는 "현재 위치"에서
읽고 그 위치를 앞으로 옮깁니다. 그래서 원하는 곳을 읽으려면 `lseek`로 먼저 위치를 옮겨야 하고,
호출 두 번 사이에 다른 스레드가 같은 fd로 `lseek`를 하면 엉뚱한 곳을 읽습니다. `pread`는 읽을
위치를 인자로 받고 **현재 위치를 건드리지 않습니다**. 호출 한 번이 그 자체로 완결됩니다. 블록
번호 하나로 그 블록만 읽어 오는 PostgreSQL에 필요한 것이 정확히 이것입니다.

블록 하나를 읽는 호출은 한 줄입니다. 2절의 예처럼 세그먼트 1의 8928번째 블록이라면 이렇습니다.

```c
r = pread(fd, buf, 8192, (off_t) 8928 * 8192);
```

`r`, 즉 `pread`의 반환값은 네 가지입니다.

| 반환값 | 뜻 |
|---|---|
| 8192 | 요청한 만큼 다 읽었다 |
| 0 | 파일 끝. 그 위치에 바이트가 없다 |
| −1 | I/O 실패. 이유는 `errno`에 |
| 0 < r < 8192 | 일부만 읽었다 |

## 4 · 블록이 몇 개인지는 파일이 안다

없는 블록을 읽지 않으려면 "블록이 몇 개인가"를 먼저 알아야 합니다. PostgreSQL은 그 값을 지난 장의
`mdnblocks()`로 얻습니다. 각 세그먼트의 파일 크기를 8192로 나눈 몫을 더한 것입니다.

이 값은 카탈로그의 `relpages`가 아니라 **파일 크기**에서 왔다는 점을 다시 강조합니다. PostgreSQL
자신도 테이블을 훑을 때 `mdnblocks()`, 즉 파일 크기를 믿습니다. 파일이 곧 진실입니다.

```sql title="psql"
select pg_relation_size('lab') / 8192 as blocks, relpages
  from pg_class where relname = 'lab';
```
```
 blocks | relpages
--------+----------
      1 |        0
(1 row)
```

`pg_relation_size()`는 main fork의 파일 크기를 더해 돌려주는 함수입니다. 8192로 나누면 블록 수 1이 나옵니다.
`relpages`는 아직 0입니다. 02장에서 본 대로 `relpages`는 `ANALYZE`나 `VACUUM` 같은 작업이 돌아야 갱신되는
통계값인데, `lab`은 만든 뒤 그런 작업을 거친 적이 없습니다. 파일에는 이미 블록 하나가 있습니다.

## 5 · 파일에는 아직 없을 수 있다

여기까지 읽었다면 이렇게 해 보고 싶을 것입니다. 테이블에 행을 넣고, 파일을 바로 읽어서 그 행이 있는지
봅니다. 그러면 대개 **없습니다**.

```sql title="psql"
create table fresh (x int);
insert into fresh values (1), (2), (3);
select pg_relation_filepath('fresh'), pg_relation_size('fresh');
```
```
 pg_relation_filepath | pg_relation_size
----------------------+------------------
 base/16384/133053    |             8192
(1 row)
```

블록 하나가 생기긴 했습니다. 그런데 그 안을 보면 전부 0입니다.

```sh title="shell"
hexdump -C $PGBASE/pgdata/base/16384/133053
```
```
00000000  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
*
00002000
```

`hexdump -C`는 파일의 바이트를 16진수로 찍는 리눅스 명령입니다(읽는 법은 06장에서 자세히 봅니다). 첫 줄은
오프셋 0부터 16바이트이고, `*`는 앞 줄과 같은 내용이 반복된다는 뜻이며, 마지막 `00002000`은 파일 끝의
오프셋 8192입니다. 8192바이트가 전부 0이라는 뜻입니다.

행 세 개는 어디 갔을까요? 메모리에 있습니다. PostgreSQL은 `INSERT`를 받으면 먼저 파일을 8 KB
늘려 자리를 잡고(그래서 크기는 8192입니다), 행은 **shared buffer**(공유 메모리의 8 KB 프레임)에
쓰며, 변경 기록은 WAL이라는 별도 파일에 남긴 뒤 곧바로 성공을 알립니다. 테이블 파일의 그
블록은 나중에, 그 프레임이 디스크로 내려갈 때 비로소 채워집니다.
그 "나중"은 몇 초일 수도, 몇 분일 수도 있습니다.

이 시점에 행 세 개는 shared buffer와 WAL에만 있고, 테이블 파일에는 없습니다. 파일에는 0으로
가득한 블록 하나뿐입니다.

```sql title="psql"
checkpoint;
```
```sh title="shell"
hexdump -C $PGBASE/pgdata/base/16384/133053 | head -3
```
```
00000000  03 00 00 00 88 8d ba b7  cc f2 00 00 24 00 a0 1f  |............$...|
00000010  00 20 04 20 00 00 00 00  e0 9f 38 00 c0 9f 38 00  |. . ......8...8.|
00000020  a0 9f 38 00 00 00 00 00  00 00 00 00 00 00 00 00  |..8.............|
```

`CHECKPOINT`는 shared buffer에 있는 변경된 프레임을 전부 파일로 내려보내라는 명령입니다. 이
뒤에는 같은 블록에 바이트가 채워져 있습니다. 이 바이트가 무엇인지는 다음 장에서 읽어 봅니다. 지금은
두 가지만 챙기면 됩니다. 파일에는 **0으로만 된 블록**이 있을 수 있다는 것, 그리고 행을 보려면
파일에 내려간 뒤여야 한다는 것입니다.

!!! danger "Trap"
    테이블 파일의 내용은 서버가 아는 것보다 늦습니다. `count(*)`는 3인데 파일에는 행이 없는 순간이
    정상적으로 존재합니다. 방금 만들거나 바꾼 테이블의 파일을 들여다볼 때는 **`CHECKPOINT`** 뒤에 봐야
    합니다.

!!! note "Design note"
    왜 바로 파일에 쓰지 않을까요? 행 하나를 넣을 때마다 8 KB 블록을 디스크에 쓰면 너무 느리고,
    같은 블록이 곧 또 바뀔 것이기 때문입니다. 대신 WAL에 변경 기록만 순서대로 붙여 두면 훨씬
    싸고, 서버가 죽어도 WAL을 다시 적용해 복구할 수 있습니다. 이 구조는 이후 수업 과정과
    프로젝트에서 버퍼 풀을 다루며 자세히 봅니다. 지금은 "파일은 늦게 바뀐다"는 사실만 기억하면 됩니다.

## 6 · 정리

- 테이블 파일은 8192바이트 블록이 빈틈없이 이어진 배열입니다. 파일 헤더도 색인도 없습니다.
- 블록 번호는 테이블 전체에 하나로 매깁니다. 세그먼트 번호는 `blkno / 131072`, 세그먼트 내부 위치는
  `(blkno % 131072) × 8192`입니다. 앞쪽 세그먼트가 전부 꽉 차 있기 때문에 이 나눗셈이 맞습니다.
- `pread`는 위치를 인자로 받아 현재 위치를 건드리지 않고 읽습니다. 블록 수는 `mdnblocks()`로
  미리 압니다.
- 파일에는 아직 안 내려간 행이 있을 수 있습니다. 직접 만든 테이블은 `CHECKPOINT` 뒤에 읽어야 합니다.
