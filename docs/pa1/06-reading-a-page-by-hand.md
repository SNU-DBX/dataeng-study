# 06 · 페이지를 손으로 읽기

!!! abstract "목표"
    같은 페이지를 두 방향에서 살펴봅니다. 파일의 바이트를 `hexdump`로 직접 읽는 쪽과, PostgreSQL이
    `pageinspect`로 풀어서 보여 주는 쪽입니다. 둘을 맞춰 보는 절차를 익혀 두면 앞으로 어떤 페이지든
    바이트 단위로 검산할 수 있습니다.

앞의 두 장에서 `lab`의 페이지 헤더와 라인 포인터를 손으로 풀었고, 05장에서는 라인 포인터를
`heap_page_items()`로 맞춰 보기도 했습니다. 이 장에서는 그 도구들을 정리합니다. 04장, 05장을
읽으면서 궁금했던 "이 값이 맞나"를 이 장의 방법으로 언제든 확인하면 됩니다.

---

## 1 · 페이지를 보는 두 가지 방법

페이지를 보는 방법은 둘입니다.

| 어디서 | 무엇을 보나 | 도구 |
|---|---|---|
| 파일 | 디스크에 마지막으로 내려쓴 바이트 | `hexdump` |
| 서버 | shared buffer에 있는 현재 페이지 | `pageinspect` extension의 `get_raw_page()` 등 |

03장 5절에서 본 대로 둘은 다를 수 있습니다. 서버 쪽이 항상 최신이고, 파일은 `CHECKPOINT` 뒤에야
따라옵니다. 그래서 둘을 맞춰 볼 때는 먼저 `CHECKPOINT`를 해야 합니다.

---

## 2 · `hexdump`

파일 쪽은 03장과 04장에서 이미 쓴 리눅스의 `hexdump -C`입니다. 왼쪽이 파일 오프셋(16진수), 가운데가
바이트 16개, 오른쪽이 같은 바이트를 글자로 찍은 것입니다.

```sh title="shell"
hexdump -C $PGBASE/pgdata/base/16384/132971
```
```
00000000  03 00 00 00 18 21 a4 b7  70 6b 00 00 24 00 70 1f  |.....!..pk..$.p.|
00000010  00 20 04 20 00 00 00 00  d0 9f 60 00 a0 9f 58 00  |. . ......`...X.|
00000020  70 9f 5e 00 00 00 00 00  00 00 00 00 00 00 00 00  |p.^.............|
00000030  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |................|
*
00001f70  a5 39 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |.9..............|
00001f80  03 00 05 00 03 09 18 0f  03 00 00 00 01 00 00 00  |................|
00001f90  00 00 00 00 00 00 00 00  0f ed 95 9c ea b8 80 00  |................|
00001fa0  a5 39 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |.9..............|
00001fb0  02 00 05 00 01 09 18 17  02 00 00 00 00 00 00 00  |................|
00001fc0  ff ff ff ff ff ff ff ff  ff ff ff ff 00 00 00 00  |................|
00001fd0  a5 39 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |.9..............|
00001fe0  01 00 05 00 02 09 18 00  01 00 00 00 01 00 00 00  |................|
00001ff0  cb 04 fb 71 1f 01 00 00  09 6b 69 6d 79 22 00 00  |...q.....kimy"..|
00002000
```

`*`는 "앞 줄과 같은 내용이 반복된다"는 뜻입니다. 0x24부터 0x1f70 직전까지가 전부 0, 즉 04장에서 본
빈 공간 [`pd_lower`, `pd_upper`) = [36, 8048)입니다. 페이지 하나가 한눈에 들어옵니다. 앞에 페이지
헤더와 라인 포인터 36바이트, 긴 0, 끝에 튜플 셋이 있습니다. 오른쪽 열의 `kim`은 1번 튜플의 `name`
값이 그대로 보이는 것이고, 그 옆의 `y"`는 문자열이 아니라 날짜 컬럼의 바이트 `79 22`가 우연히 글자로
찍힌 것입니다.

일부만 보려면 `-s`(시작 오프셋)와 `-n`(바이트 수)을 주면 됩니다. 05장에서 푼 1번 튜플이면 오프셋
8144에서 48바이트입니다.

```sh title="shell"
hexdump -C -s 8144 -n 48 $PGBASE/pgdata/base/16384/132971
```
```
00001fd0  a5 39 00 00 00 00 00 00  00 00 00 00 00 00 00 00  |.9..............|
00001fe0  01 00 05 00 02 09 18 00  01 00 00 00 01 00 00 00  |................|
00001ff0  cb 04 fb 71 1f 01 00 00  09 6b 69 6d 79 22 00 00  |...q.....kimy"..|
00002000
```

마지막 줄의 `00002000`은 출력이 끝난 오프셋, 8144 + 48 = 8192입니다. `-s`에는 10진수 8144나 16진수
`0x1fd0` 어느 쪽을 줘도 됩니다.

파일이 여러 세그먼트일 때는 03장의 계산으로 세그먼트와 세그먼트 내부 오프셋을 먼저 구해야 합니다.
`seg_demo`의 블록 140000이면 `133056.1` 파일에 `-s 73138176 -n 8192`입니다.

## 3 · `pageinspect`

서버 쪽에서 볼 때는 `pageinspect`라는 extension을 씁니다. PostgreSQL 소스 트리의 `contrib/pageinspect`에
있으며, 서버와 별도로 아래처럼 빌드해서 설치한 뒤 데이터베이스에서 `CREATE EXTENSION`으로 켜서
씁니다. 빌드와 설치는 [01장](./01-environment-setup.md)에서, `CREATE EXTENSION`은 05장에서 이미
했습니다.

```sh title="shell"
cd $PGBASE/postgres
make -C contrib/pageinspect install
```
```sql title="psql"
create extension if not exists pageinspect;
```

사용할 함수는 크게 다음과 같습니다.

| 함수 | 돌려주는 것 |
|---|---|
| `get_raw_page(relname, blkno)` | 페이지 8192바이트 그대로(`bytea`) |
| `page_header(bytea)` | 페이지 헤더를 필드별로 풀어서 한 행으로 |
| `heap_page_items(bytea)` | 라인 포인터마다 한 행. 튜플 헤더 값도 같이 |

### 3.1 · `get_raw_page()`: 바이트 그대로

```sql title="psql"
select encode(substring(get_raw_page('lab', 0) from 1 for 40), 'hex');
```
```
                                      encode
----------------------------------------------------------------------------------
 030000001821a4b7000000002400701f0020042000000000d09f6000a09f5800709f5e0000000000
(1 row)
```

`substring(… from 1 for 40)`은 처음 40바이트입니다. `bytea`의 `substring`은 **1부터** 센다는 것만
조심하면 됩니다. 2절의 `hexdump` 첫 40바이트와 나란히 놓으면 이렇습니다.

```
file:   03000000 1821a4b7 706b 0000 2400 701f 0020 0420 00000000 d09f6000 a09f5800 709f5e00 00000000
server: 03000000 1821a4b7 0000 0000 2400 701f 0020 0420 00000000 d09f6000 a09f5800 709f5e00 00000000
                          ^^^^
                          pd_checksum
```

바이트 8 – 9, `pd_checksum`만 다릅니다. 파일에는 0x6b70이 있고 서버 쪽은 0입니다. 체크섬은 페이지를
디스크에 **쓰는 순간** 계산하는 값인데, 버퍼 안의 페이지에 써넣는 것이 아니라 디스크로 나갈
복사본에만 넣습니다. 이 페이지는 메모리에서 만들어진 뒤 아직 디스크에서 다시 읽힌 적이 없어서 버퍼
쪽이 0입니다. 그 외의 바이트는 `CHECKPOINT` 뒤라면 전부 같습니다.

반대로 디스크에서 읽어 온 페이지는 파일 바이트가 그대로 버퍼에 복사되므로 체크섬도 같이 들어
있습니다.

!!! note "Design note"
    체크섬은 디스크가 바이트를 바꿔치기하지 않았는지 확인하는 용도라 디스크로 나가는 순간에만 의미가
    있습니다. 메모리 안의 페이지는 계속 바뀌므로 매번 다시 계산해 넣는 것은 낭비입니다. 그래서 쓰기
    직전에 한 번 계산하고, 읽어 들일 때 한 번 검사합니다. `PageIsVerified()`가 체크섬이 켜져 있으면
    `pg_checksum_page()`로 다시 계산해 비교하는 것이 그 검사입니다.

튜플 하나도 같은 방법으로 꺼낼 수 있습니다. 1번 튜플은 오프셋 8144, `substring`으로는
8145부터입니다.

```sql title="psql"
select encode(substring(get_raw_page('lab', 0) from 8145 for 48), 'hex');
```
```
                                              encode
--------------------------------------------------------------------------------------------------
 a539000000000000000000000000000001000500020918000100000001000000cb04fb711f010000096b696d79220000
(1 row)
```

2절의 `hexdump -C -s 8144 -n 48`과 한 바이트도 다르지 않습니다.

### 3.2 · `page_header()`: 페이지 헤더를 풀어서

```sql title="psql"
select * from page_header(get_raw_page('lab', 0));
```
```
    lsn     | checksum | flags | lower | upper | special | pagesize | version | prune_xid
------------+----------+-------+-------+-------+---------+----------+---------+-----------
 3/B7A42118 |        0 |     0 |    36 |  8048 |    8192 |     8192 |       4 |         0
(1 row)
```

04장 2.1절에서 푼 값 그대로입니다. `checksum`이 0인 이유는 3.1절과 같습니다.

### 3.3 · `heap_page_items()`: 라인 포인터마다 한 행

```sql title="psql"
select lp, lp_off, lp_flags, lp_len from heap_page_items(get_raw_page('lab', 0));
```
```
 lp | lp_off | lp_flags | lp_len
----+--------+----------+--------
  1 |   8144 |        1 |     48
  2 |   8096 |        1 |     44
  3 |   8048 |        1 |     47
(3 rows)
```

`lp`가 05장의 번호, 나머지 셋이 라인 포인터의 세 필드입니다. 이 함수는 열이 더 많습니다.
`select *`로 보면 `t_xmin`, `t_infomask`, `t_hoff`, `t_bits`, `t_data` 같은 열이 따라오는데, 전부
라인 포인터가 가리키는 **튜플 안**에서 읽어 온 값입니다. 그중 필요한 것은 07장부터 튜플을 풀 때
하나씩 봅니다.

## 4 · 검산 절차

앞으로 페이지 하나를 손으로 읽을 때 순서는 늘 같습니다.

1. `CHECKPOINT`. 파일과 서버를 맞춥니다. 서버를 껐다 켜도 됩니다. 종료할 때 checkpoint를 하기
   때문입니다.
2. `hexdump -C -n 24`로 페이지 헤더를 봅니다. 바이트 12, 14, 16에서 `pd_lower`, `pd_upper`,
   `pd_special`을 읽습니다(little-endian). `page_header()`와 맞춰 봅니다.
3. `(pd_lower − 24) / 4`로 라인 포인터 개수를 구합니다. `hexdump -C -s 24 -n <개수 × 4>`로 라인
   포인터 배열을 보고, 4바이트씩 32비트 값으로 읽어 `w & 0x7fff`, `(w >> 15) & 3`,
   `(w >> 17) & 0x7fff`로 풉니다. `heap_page_items()`의 `lp_off`, `lp_flags`, `lp_len`과 맞춰
   봅니다.
4. NORMAL인 라인 포인터의 `lp_off`, `lp_len`으로 `hexdump -C -s <lp_off> -n <lp_len>`을 합니다.
   그것이 튜플 하나입니다.

4번에서 꺼낸 바이트가 07장부터의 재료입니다.

---

## 5 · 정리

- 파일 쪽은 `hexdump -C`, 서버 쪽은 `pageinspect`의 `get_raw_page()`, `page_header()`,
  `heap_page_items()`입니다. `CHECKPOINT` 뒤에는 `pd_checksum`을 빼고 전부 같습니다.
- `get_raw_page()`의 `bytea`를 `substring`할 때는 1부터 셉니다. 파일 오프셋 8144는
  `from 8145`입니다.
- `heap_page_items()`의 `lp`, `lp_off`, `lp_flags`, `lp_len`이 라인 포인터이고, 나머지 열은 튜플
  안의 값입니다.
